项目概览

一个学生公寓管理系统，覆盖学生与管理员两种角色的日常事务：请假审批、报修、进出打卡、卫生评分、缴费、公告、访客登记。

项目的重点不是功能数量，而是两次重构 + 一次前后端联调。

关键技术点

1. 数据访问层收口

改造前每个页面自己开库、自己拼 SQL、自己按列位置取数据：

Cursor cursor = db.rawQuery(sql, args);
while (cursor.moveToNext()) {
    Integer id = cursor.getInt(0);        // 列位置硬编码，全项目 89 处
    String account = cursor.getString(1);
}

改造后用 getColumnIndexOrThrow("列名")，建表字段顺序变化也不会静默串数据。

2. 手写 DAO → Room

手写 DAORoom
建表手写 create table 字符串由 @Entity 生成，SQL 与字段不可能对不上
写错代价运行时才炸编译期报错（把每条 SQL 拿到内存 SQLite 上真跑）
事务beginTransaction 三件套一个 @Transaction 注解
联表结果往实体里塞“有时有值”的字段@Embedded + 独立 POJO

3. 客户端与服务端打通

客户端用 Retrofit 调用后端 REST 接口。网络开发真正的难点不是“发个请求”，而是分清三层失败：

层表现典型原因给用户的提示
传输层onFailure（ConnectException / 超时）后端没启动、IP 不对、不同网段连不上服务器
HTTP 层isSuccessful() == false400 参数 / 404 路径 / 500 服务端 bug按状态码区分
业务层body().getCode() != 0权限不足、状态冲突直接显示后端 message

4. 统一响应与异常语义

HTTP场景
400参数校验失败 / 业务规则不满足
404路径不存在 / 资源不存在
405请求方法不支持
503数据库连不上（不是 500）
关键取舍：数据库不可用属于服务端依赖失败，语义上应返回 503 而非 500； 并且要把原因写进响应体，否则调用方只看到“服务器内部错误”，无从定位。

数据源与安全策略

原则：服务端是唯一权威数据源。客户端可以有本地数据，但它只是"暂存"，不参与裁决。

角色职责
服务端 · MySQL唯一权威。写入、状态流转、时间戳全部由它决定
客户端 · Room仅作本地暂存 / 离线展示；联网后以服务端返回为准，不做本地优先
冲突处理以服务端最新数据覆盖本地，客户端不参与判断谁对

为什么"服务端权威"顺带解决了安全问题

风险做法证据
SQL 注入 全部 SQL 走 #{} 预编译占位符，全项目 0 处 ${} 字符串拼接 mapper/*.xml
客户端伪造字段 status / date / orderDate 由服务端赋值，客户端传了也无效 RepairsService.create
越权提交 服务端校验 userType == 学生 才允许提交报修（管理员 id 会被拒） RepairsService.create
本地库被篡改 本地只是缓存，改它不影响权威数据；下次同步即被服务端覆盖 设计原则
一句话：客户端不可信，所以它只负责"显示"，不负责"决定"。
凡是"谁的数据算数""这个状态能不能变""时间取哪个"这类问题，答案一律在服务端。

落地：读和写用的是不同策略

操作策略为什么这么选
读 · 学生列表 网络优先 → 成功则整体覆盖本地缓存 → 失败才回退缓存 离线也能看一眼，但界面会明确标注「数据来源：本地缓存，可能过期」
写 · 提交报修 只走服务端，不做缓存回退 提交失败必须让用户知道失败——不能用本地"假装成功"

这个不对称是刻意的：读可以降级，写不能降级。让写操作"看起来成功"是最危险的一类 bug。

数据库升级：第一个真正的 Migration

新增缓存表需要把库从 v8 升到 v9。之前 v7→v8 只能用 fallbackToDestructiveMigration() （旧库是 SQLiteOpenHelper 手写的，没有 Room 的身份校验表，没法忠实迁移）； v8 之后库已是 Room 建的，所以这次写了精确迁移：只加一张表，不动老数据。

static final Migration MIGRATION_8_9 = new Migration(8, 9) {
    public void migrate(SupportSQLiteDatabase db) {
        db.execSQL("CREATE TABLE IF NOT EXISTS `cached_student` (...)");   // 不动其它表
    }
};

值得讲的两个真实缺陷修复

① 一个查询静默返回空，完全不报错。宿舍管理列表永远是空的，但同一条 SQL 在设备上手动执行却能查出数据。 根因是建表时列没有声明类型 —— SQLite 的亲和性由声明类型决定，没声明就是 NONE 亲和性、不做类型转换， 于是 where userType = ? 绑定文本 "0" 时，TEXT 和 INTEGER 匹配不上。 更反直觉的是：这个坑恰恰是“有人为了安全改用占位符”那一刻才爆发的。

② 数据库连不上只报“500 服务器内部错误”。调用方完全看不出是 MySQL 没启动。 加了 DataAccessException → 503 的独立处理器，把原因直接写进响应体； 同时确认了一个容易误解的行为 —— MySQL 中途重启后，后端不用重启也能自动恢复（连接池会重建连接）。
